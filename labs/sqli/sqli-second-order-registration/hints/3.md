Your registered **username** is stored safely (the INSERT is parameterised) but
`/me/referrals` rebuilds a raw query by concatenating that stored username. So the
payload must survive being stored verbatim and then act as SQL when the second
codepath reads it back.

Shape of the attack — the username has to:

- close the string literal the referrals query opens around `owner = '<username>'`,
- add a `UNION SELECT` whose column count matches the referrals `SELECT` (two
  columns) and whose first column is the admin `session_secret` from the
  `accounts` table, and
- comment out the trailing quote the sink appends.

Then drive it across endpoints: register with that username, log in, load
`/me/referrals` to trigger the sink and read the leaked secret, and submit it to
`/solve`. Hint 4 gives the exact payload and the four requests.
