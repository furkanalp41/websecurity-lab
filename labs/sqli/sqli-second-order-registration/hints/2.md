This is a **second-order** (stored) SQL injection. `/me/referrals` rebuilds a raw
query by concatenating your stored username into a string like:

```
SELECT code, invited_email FROM referrals WHERE owner = '<your username>'
```

So your username lands _inside a single-quoted string literal_ in that query —
even though it was harmless when it was written. That means the payload has to
live in your **username**, not in the referrals request. Whatever you register as
your name is what gets spliced in here.

Two things to plan for:

- The query selects **two** columns (`code`, `invited_email`). If you want to add
  your own rows with `UNION SELECT`, your select must also return two columns.
- The sink wraps your value in quotes and appends a trailing `'`. Your payload
  has to open cleanly, do its work, and neutralise that leftover quote so the
  final statement is still valid SQL.

Where might a juicy secret live? There is more than one table. You cannot query
the other one directly through the UI — but a `UNION` in this query can.
