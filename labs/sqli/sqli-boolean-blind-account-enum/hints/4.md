Target the `admin` row's `password_hash` and read it one character at a time.
Postgres `substring(password_hash from N for 1)` gives you the Nth character;
wrap it in `ascii(...)` to compare code points (no collation surprises). The
oracle answers a `≤` question, which is what makes a binary search possible:

```
POST /forgot
{"username": "admin' AND (ascii(substring(password_hash from 1 for 1)) <= 64)-- -"}
```

`X-Account-Exists: true` means "character 1's code is ≤ 64"; `false` means "> 64".
Binary-search the code for each position instead of trying all candidates:

- Keep a low/high bound over the printable range the hash uses. A bcrypt hash only
  contains `$ . / A-Z a-z 0-9`, whose ASCII codes run from `0x24` to `0x7a`.
- Halve the range each request: send the midpoint as the `<=` value, move the
  high bound down on `true` and the low bound up on `false`.
- ~7 requests pin down one character; repeat for positions 1 through 32.

Assemble the 32 characters in order to get the hash prefix, then claim the flag:

```
POST /solve
{"prefix": "<the 32 characters you recovered>"}
```

On a match the response is `{"flag": "FLAG{...}"}`. Automate the loop — doing 32
binary searches by hand is tedious and error-prone; a ~40-line script (see the
shape in `tests/exploit.py` if you want to compare afterwards) recovers the prefix
in a few seconds. Note that `/solve` itself is written with a bound parameter, so
do not waste time trying to inject there — `/forgot` is the only door.
