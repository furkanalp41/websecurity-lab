The endpoint looks like a dead end: `/beacon?ref=anything` returns `204 No
Content` every single time. No body, no error, no header that changes. Resist the
urge to conclude "nothing reaches SQL" — you have simply lost the _visible_
channels, not the vulnerability.

List the observables an attacker can actually influence on this request. Status
code: fixed. Body: empty. Headers: constant. That leaves exactly one thing you can
still affect from the outside — **the time the request takes to come back**.

So reframe the goal. You are not going to _read_ data out of the response. You are
going to make the database **pause on command**, and use the presence or absence
of that pause as a one-bit answer. If you can phrase a yes/no question in SQL and
make "yes" take noticeably longer than "no", you can ask as many questions as you
like, one request at a time. What MySQL function makes a query deliberately wait?
