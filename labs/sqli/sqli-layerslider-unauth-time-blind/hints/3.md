Put the delay behind a yes/no question about the admin hash. The `id` parameter
lands in `... WHERE id = <id> AND flag_hidden = 0`, so this stays valid SQL:

```
id = 0 OR (SELECT SLEEP/**/(0.6) FROM wp_users
           WHERE user_login=0x61646d696e AND (<condition>))
```

When `<condition>` is true the admin row matches and the subquery sleeps; when
false, no row matches and the response is instant. Use that to read one character
of `user_pass` at a time by its ASCII code:

```
<condition> = ASCII(SUBSTRING(user_pass,POS,1)) >= VAL
```

`user_pass` here is 16 lowercase hex characters (`0-9a-f`). Binary-search `VAL`
for each `POS` (about 4 requests per character), and probe several positions
concurrently to beat the rate limiter — but keep your concurrency modest, or a
fast (FALSE) request can queue behind another request's SLEEP and read as slow. If
you get an HTTP 429, back off and retry; it is a rate-limit block, not a timing
answer. Submit the recovered 16 hex chars to `POST /solve` as `{"hash":"..."}`.
