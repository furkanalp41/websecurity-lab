Your `filter` is being pasted into the SQL string, not bound as a parameter. The
query is roughly:

```
SELECT id, title FROM reports WHERE title LIKE '%<filter>%'
```

So you can break out of the `'%...%'` literal. Close the quote, add your own SQL
with `AND`, and comment out the trailing `%'` the server appends with `-- ` (note
the trailing space). Prove you control the row count:

- `searchReports(filter: "")` → matches everything → rows come back (TRUE).
- `searchReports(filter: "' AND 1=2 -- ")` → contradiction → no rows (FALSE).

If those two behave differently, the row count now reflects the **truth value** of
any condition you inject. This is **boolean-blind SQL injection**: one true/false
bit per probe, no data echoed back.

Now aim the condition at the secret. It is not in `reports` — it is a single column
`batch_flag` in a separate `secrets` table. You cannot select it directly, but you
_can_ ask yes/no questions about it with a scalar sub-select and Postgres'
`substr()`:

```
' AND (SELECT substr(batch_flag,1,1) FROM secrets LIMIT 1)='0' --
```

That returns rows iff the **first** character of `batch_flag` is `0`. Which
characters do you even need to try? (It is 40 lowercase-hex characters.) And how
many separate HTTP requests would 40 positions × 16 candidates take if you sent one
probe at a time — versus if you used GraphQL the way hint 3 suggests?
