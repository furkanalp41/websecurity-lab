Upload an SVG avatar and look closely at how the profile page shows it. Request
`POST /avatar` (multipart, field `avatar`, Content-Type `image/svg+xml`, body
starting with `<svg`), then open the returned `/u/<uuid>` and view source.

Your avatar is embedded with `<object data="/avatars/<uuid>.svg"
type="image/svg+xml">`, **not** `<img src=…>`. That distinction is everything.
An SVG shown with `<img>` is rasterised as an image and its scripts never run —
but an SVG loaded as a _document_ (which `<object>`, `<iframe>` and navigating
straight to `/avatars/<uuid>.svg` all do) executes its `<script>` in the page's
origin, because it is served with `Content-Type: image/svg+xml`.

The upload check only looks at the declared MIME type and that the bytes start
with `<svg`. It never removes a `<script>`. So an SVG can carry live JavaScript.

Running a script in _your own_ browser gets you nothing, though. Whose browser
holds something worth stealing, and what feature hands that browser a URL?
