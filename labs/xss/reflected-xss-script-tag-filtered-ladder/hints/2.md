You do not need a `<script>` tag at all. Plenty of elements execute JavaScript
from an event handler the moment they load — and the blocklist names only
`onerror=`. The cleanest bypass is an SVG (or image) with an `onload` handler,
which fires automatically with no click:

```
<svg onload="...JS here...">
```

None of `<script`, `</script`, `javascript:`, `onerror=` appears in that, so the
filter passes it through untouched.

The delivery path is the same one you have seen before:

1. `POST /report` (the "report a page to staff" feature) queues a same-site path
   that the admin bot then visits — carrying its `session` cookie, which is
   **not** `HttpOnly`, so `document.cookie` can read it. The bot only navigates
   and waits, so your payload must fire **on load** (which `onload` does).
2. Send the cookie somewhere you can read it. The only listener reachable from
   the bot's network is the collector at `http://collector:9000/` (that network
   has no internet route).

How do you fire an HTTP GET to another host from inside a handler without
worrying about CORS? An image load — `new Image().src = '...'` — does exactly
that.

(Stuck on `<img onerror>` specifically? The blocklist matches the literal
`onerror=`. HTML allows whitespace around the `=`, and `onerror =` — with a
space or tab — is not that substring. The parser still wires up the handler.)
